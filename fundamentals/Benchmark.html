第 2 章 Benchmark ​

1. 简介 ​

推理负载 Benchmark（Inference Workload Benchmark）：评估已经部署的推理服务，在给定请求负载下测量 TTFT、TPOT、吞吐量、P99 延迟等工程指标。它关注的是模型“运行得快不快、稳不稳”，也常被称为 AI Infra Benchmark。

推理服务的指标分为两类：一类描述单个请求的响应速度，称为延迟；另一类描述系统的总体产出能力，称为吞吐。二者回答不同的问题，不能相互替代。

2. 延迟是什么 ​

延迟（latency）是从单个用户的角度看：我的请求要等多久。比如：

  • TTFC：多久听到第一段声音；
  • 端到端延迟：多久拿到完整音频；
  • p95 延迟：最慢的那 5% 请求要等多久。

先定义两个词：

  • TTFT（time to first token）：从发请求到收到第一个 token 的时间。
  • TPOT（time per output token）：之后每多生成一个 token 平均要多久。
  • TTFC (time to first chunk) : 指的是语音模型里流式 TTS 里的首包延迟，即从发请求到客户端收到第一段音频的时间

2.1 为什么 TTS 不直接用 TTFT ​

TTS 的 LLM 生成的是 speech token（语音 token），它不能直接播放，必须攒够一批之后经过 Flow DiT 变成 mel 频谱，再经过 HiFT 变成波形，才算一段能听的音频。这一段音频就叫 chunk。所以 TTS 关心的是第一个 chunk 什么时候到，而不是第一个 token 什么时候出来。

2.2.2 TTFC 由哪几段时间组成 ​

  • 入口：网络传输、HTTP 和 API 解析、构造请求、派发给第一个 stage。
  • 输入处理：
    • 预处理：音频解码、重采样、图像处理、分词等，一般在 CPU 上。
    • 编码器：音频或视觉编码器，把原始输入变成模型能用的特征。
  • 文本模型（thinker）产出首批文本：排队、prefill，再 decode 出第一批文本 token。很多语音模型要攒够若干个 token 才开始转发给下一级，所以这一段往往比纯文本的 TTFT 更长一些。
  • 语音 token 模型（talker）产出首批 codec 帧：排队、prefill，再 decode 出足够组成第一个音频块的帧数。
  • 声码器（vocoder / code2wav）产出首段波形：先攒够第一个块需要的帧（有些声码器还要额外的前后文帧），可能还要等凑 batch，然后解码成波形。
  • 出口：编码成流式响应（PCM 或 SSE），经网络发回客户端。

3. 吞吐是什么 ​

吞吐（throughput）是单位时间内系统完成了多少工作。单位有两种：

  • tok/s：每秒生成多少个 token。cookbook 里"只测 LLM"的那张表用的是这个，比如 batch 16 时 4,260 → 6,388 tok/s。
    • 单请求时，吞吐就是由 TTFT 和 TPOT 决定的：一个用户每秒收到多少 token，约等于 1 ÷ TPOT。
    • 系统吞吐：整台机器每秒生成多少 token，是所有用户加起来的总数。
  • req/s：每秒完成多少个请求。比如 c16 时 18.02 → 21.08 req/s。

4. 两者的关系 ​

可以用排队来想象。假设服务器同时处理 N 个请求，每个请求平均耗时 L 秒，那么：

吞吐 ≈ N ÷ L

所以提高吞吐有两种办法：

  1. 让每个请求更快（L 变小）：吞吐上升，延迟也下降，两全其美。
  2. 同时处理更多请求（N 变大）：吞吐上升，但每个请求可能等得更久。
